## 1. W4：残り5エリア（推奨＝まず2つだけ）

### 対象と優先順
島の地図（`js/ui_konron_map.js` KONRON_AREAS）9エリアのうち、歩けるのは現在4つ（city/race/onsen/beach）。残り5つ：

| 順 | id | 名前 | 徒歩でつなぐ先 | 備考 |
|---|---|---|---|---|
| ① | `fishing` | ホシウオ村 | beach ⇄ fishing | 食事・スポットの結線先が濃い。最優先 |
| ② | `falls` | ルミナ瀑布 | onsen ⇄ falls | 撮影スポットが強い |
| ③ | `cliff` | キビシス崖線 | falls ⇄ cliff | 星見＝夜の独白が映える |
| ④ | `sanctum` | 竜舎林・ダコン湖 | falls ⇄ sanctum | ポロ随行と相性◎ |
| ⑤ | `okuchi` | 奥地・霧の彼方 | cliff ⇄ okuchi | **薄く**（アートバイブル§0.5＝霧の彼方の神秘。入口1つ＋「？」程度） |

**★①②を作って一度ユーザーに触ってもらい、面白ければ③〜⑤へ進む。**5つ一気に作らない
（歩くモード全体が「作ってから面白くないと判明」した前例がある）。

### 1エリアの作り方（この順序で・省略不可）
1. **背景1枚**（Higgsfield・約2cr）。**city.webp を参照画像に渡す**方式が唯一うまくいった方法：
   `media_import_url` で `https://takakazuaikawa-hue.github.io/mimi-dragon-race-game/images/scene/konron/city.webp`
   を取り込み、`nano_banana_pro` に `medias:[{role:"image", value:<media_id>}]` で渡す（role は自動で "image" に矯正される）。
   プロンプトは「参照の**画風と画角の両方**に一致：真上寄り・崖の垂直面を作らない・建物は屋根が主に見える大きさ／
   ただし建物と地形は真似ない」＋そのエリア固有の内容。`pixel` の語は絶対に入れない。
   → 2k upscale → `sharp` で 1920×1440 webp q86 → `images/scene/konron/<id>.webp`。
2. **当たり判定 32×24**：スクラッチパッドの `cellgrid.js`（セル番号入りグリッド合成）→ 目視で起こす →
   `redzone.js`（赤塗り＋BFS）で絵と突き合わせ → **ALL GREEN** まで直す。`KW_AREAS` に追記。
3. **入口（doors）**：**新しい機能を作らない**。そのエリアの `spots`（上表のKONRON_AREAS参照）へ渡すだけ。
   最低限：📷撮影1つ（`kwShoot(<spotId>)`・`stay:true`）／🍢か🍧の屋台1つ（`kwStall(タイトル,[mealId…])`
   ＝**その場に在る品だけ**。全品目を開く `renderMeals` 直行は禁止＝設計ミスとして直した経緯あり）／
   隣エリアへの道2つ（`area:"<id>"`）／🏝️島の地図へ1つ。
4. **散歩の中身**（これが本体）：`KW_MUSE[<id>]` に**独白5行**、`KW_FINDS[<id>]` に**役に立たない発見6個**。
   既存4エリアの文体に合わせる（一人称の気づき・オチをつけない・1行30字以内）。
   ⚠️ 発見は報酬にしない（コイン・進行・強さに触れない）。
5. **接続**：隣エリア側にも戻りの door を足す（片道にしない）。`KW_V` バンプ。
6. **検証**：ソルバ不要だがBFS必須。実機で **そのエリアを自分で一周**（詰まり・帰り道・屋台の中身）。
   4エリア時代の実測値＝到達マス city127 / race121 / onsen139 / beach170。**100〜180マス**が目安（狭すぎ・広すぎの判断基準）。

### 予算
背景5枚＝約10cr＋upscale5＝約5cr（**合計15cr程度**。残高932crに対し誤差）。①②だけなら6cr。

## 2. 任意A：ミニアニメのクリップ軽量化 → **推奨＝いまはやらない**

現物（実測）：`images/fx/clip_masterpiece.mp4` 2.9MB ／ `clip_conquer.mp4` 1.2MB ／ `clip_bloom.mp4` 0.6MB＝計4.7MB。

**この環境には ffmpeg も PIL も ImageMagick も無い**（過去セッションで確認済み。`sharp` は静止画のみ）。
つまり**再エンコードは実行不能**で、やるなら次のどれか：

- (a) **やらない**（推奨）。3本とも「初回のその瞬間だけ」再生される祝祭。常時ロードではない。
  2.9MBが実害になっている証拠がまだ無い。**測ってから直す**（先に体感の問題を確認）。
- (b) ユーザーの手元で `ffmpeg -i in.mp4 -vf scale=720:-2 -crf 30 -an out.mp4` を実行してもらう（一番安上がり）。
- (c) Higgsfield で**短く・小さく作り直す**（1本あたり動画生成のクレジットを消費。効果に対して高い）。

**先にやるべき計測**：390×700実機で masterpiece を初回再生し、`performance` で読み込み〜再生開始の実測。
1.5秒を超えるなら (b) をユーザーに依頼、超えないなら (a) で確定。**測らずに作業を始めない。**

## 3. 任意B：ずかんの回転ビューア用 GLB 18体 → **推奨＝全部はやらない**

現状：`images/rpg/turn/` にあるのは `boss1.webp` の1体のみ。残り18体。
コスト＝`image_to_3d`（Meshy）**30cr/体 × 18 = 540cr**。残高932crの**58%**。

- 回転ビューア（`js/dex_view.js`）は turn/ が無ければ**平面の絵に自動フォールバック**する＝欠けても壊れない。
- 費用対効果が最も高いのは**ボス／主だけ**（図鑑で一番見られる・一番「おっ」となる）。
- **推奨＝ボス級4〜6体だけ焼く（120〜180cr）**。雑魚を含む18体は、崑崙の他の生成（新エリア背景・
  スカウト演出・将来の物語カット）に残しておくべき予算。

やる場合の手順（G3-6で確立済み・逸脱しないこと）：
`image_to_3d` → GLB取得 → WebGL2 + 頂点シェーダのuniformで回す自前ベイク（手回し行列は失敗した）→
16コマ横並び webp → `images/rpg/turn/<id>.webp` → **保存前に「非透過ピクセルがあるか」のゲートを通す**
（空の帯を書き出した事故あり）。1体ずつ実機で回して確認。
