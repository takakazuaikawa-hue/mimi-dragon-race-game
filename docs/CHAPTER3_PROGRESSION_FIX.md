## なぜ3件をまとめるか

3件とも「第3話」という同じ一点から出ている。

- **F9** … 第3話に**入れない**人がいる（複勝・ワイドだけで遊ぶと永久に到達不能）
- **F8** … 第3話を**読むと損をする**（素直に読んだ人だけ資産が凍る）
- **ツリー事前取得** … 第3話まで、くらしツリーが**存在しないことになっている**

バラバラに直すと、片方の修正がもう片方を悪化させる。まとめて決める。

## 1. 事実（すべて確認済み）

| ED | 第5話既読 ∧ `epilogue.edFlag` |

### 1-2. F9：`wins` は単勝の的中でしか増えない

`js/ui_render.js` settleRace:

```js
if (betResult.hit) {                       // ← 式別不問で記録されている
  state.player.hitsByRank[c.race.rank] += 1;
}
if (betResult.hit && c.bet.type === "win") {   // ← wins は単勝だけ
  state.player.wins += 1;
}
```

つまり **複勝・ワイドだけで遊ぶプレイヤーは `wins` が永遠に 0** で、第3話→第4話→第5話→終章→ED のすべてに到達できない。
同じ `wins >= 1` が 🏝おでかけの解放（`js/ui_konron_map.js` / `js/progression.js`）も握っているため、**島コンテンツごと閉じる**。

★重要：救済に使える材料は既にある。`hitsByRank` は**式別不問**で貯まっている（ランク3本レールの「実力レール」がこれを読んでいる）。

### 1-3. F8：第3話を読むと総資産の主成分が凍る

- 暮らしレベル → 村価値（`VILLAGE_VALUE_BY_LEVEL`）→ 総資産の主成分 → `assetsPeak` → 第4話(100万)・第5話(1億)のゲート
- `livingLevelCap`（`js/data_ranks.js`）は **第3話を読むまで上限なし**（fail-open）、読んだ瞬間に `1 + floor(解放ノード数 / 20)` へ

| 暮らしLv | 村価値 | |
|---|---|---|
| 1 | 2,000 | |
| 5 | 500,000 | |
| **6** | **2,000,000** | ★第4話ゲートを単独で超える |
| **9** | **120,000,000** | ★第5話ゲートを単独で超える |
| 10 | 500,000,000 | |

**実機で測った2人の比較**（どちらも同じだけ的中している）

| | 第3話を先に読んだ人 | 第3話を後回しにした人 |
|---|---|---|
| 暮らしレベル | **Lv1で凍結**（経験値 99,999 が余っても昇格不可） | Lv9 まで自由に伸びる |
| 総資産 | **3,000** | **120,539,300** |
| 第4話 | 村価値では永久に届かない | 単独で超える |

そして決定的なのが、**既得レベルは下がらない**こと（`applyLivingLevelUps` は `while (v.level < cap)` なので、既に上なら何も起きない）。
→ **第3話を読む前に上げきっておけば上限は無関係**になる。つまり **読む順を知っている人だけが得をする**。

★これは「バランスが悪い」ではなく **順序の逆転**。第3話は第4話の必読条件なので避けられないのに、読むと損をする。

## 2. 直し方の案

### F9：単勝以外にも道を開く（★決裁1）

**案A（推奨）**：第3話のゲートを `wins >= 1 || 的中の合計 >= 3` にする。

```js
case "3": return chapterRead("2") && (wins >= 1 || totalHits(p) >= 3);
```

- `totalHits` は `hitsByRank` の合計＝**既にある材料**。新しい記録を足さない
- 「単勝1勝」と「複勝/ワイドで3回当てる」を等価に置く。単勝のほうが軽いので、単勝を選ぶ動機は残る
- 物語との整合：第3話は「勝ち分の守り方」の話なので、**当てて金が入った経験**があれば筋が通る（単勝である必要はない）
- ★同じ `wins >= 1` を見ている **おでかけの解放も同時に直す**（島が閉じたままでは意味がない）

**案B**：ゲートは触らず、ヒントに「単勝で当てると進む」と明記するだけ。
→ 到達不能は残る。**推奨しない**。

**案C**：`wins` の定義を「式別不問の的中」に変える。
→ 影響範囲が広すぎる（ランクの3本レール、目標、走馬灯、SNSがすべて `wins` を読む）。**推奨しない**。

---

### F8：上限の逆転を止める（★決裁2）

**案A（推奨）**：**上限の下限を引き上げる**。`livingLevelCap` の最低値を 1 → **6** にする。

```js
return Math.max(6, Math.min(LIVING_RANKS.length, 1 + Math.floor(got / LIVING_NODES_PER_LV)));
```

- 暮らしLv6 = 村価値200万 = **第4話ゲートを単独で超えられる**＝第3話を読んでも第4話への道が閉じない
- Lv7以上（第5話の1億へ向かう領域）は従来どおりツリーが要る＝**ツリーの意味は残る**
- 変更は1行。既得レベルを下げないので既存セーブは無傷

**案B**：ツリー解放前に取れなかったぶんを補填する（読んだ時点で `floor(完走数/10)` ノードを自動付与など）。
→ 実装が重く、ノードの意味が薄まる

**案C**：第4話・第5話のゲートを総資産から外す。
→ 経済設計の根幹（`docs/ENDGAME_ECONOMY_REDESIGN.md`）に触る。影響が大きすぎる

★どの案でも、**「先に読むと損」を消すことが目的**。バランス調整ではない。

### ツリー事前取得：物語で自然に得たものを「取得済み」にする（★決裁3）

ユーザーの設計：**解放前でも、物語上ミミが実際に得たものは取得済みになる。最初はフレーバー演出に見えて、ツリーが開いた瞬間に「あれは本物のノードだった、しかも今度は狙って取れる」と反転する。**

実装の形：

```js
// data_chapters.js か新ファイルに「出来事 → ノード」の表を置く
var LIFE_STORY_GRANTS = [
  { on: "firstMeal",  nodeId: "...", },   // はじめて屋台で食べた
  { on: "firstWin",   nodeId: "...", },   // はじめて勝った
  { on: "buyBuniqro", nodeId: "...", },   // はじめて自分の服を買った
  ...
];
```

- **無償**で付与する（`lifeTree.unlocked` に入れるが `lifeTree.bought` には入れない）
  → 「買った」履歴と区別され、振り直し時の扱いも既存のまま
- 付与時は既存の `showLifeCutin(node)` を再利用＝新しい演出を作らない
- **上限への影響**：事前取得が数個なら `1 + floor(n/20)` はほぼ動かない。F8案Aで下限6にするなら影響ゼロ
- ツリーが開いた時に「すでに ◯個 身につけている」と見えることで、反転が起きる

★決めるべきは **「どの出来事にどのノードを結ぶか」**。ここが物語の納得感を決めるので、ノードの実タイトルを見ながら一緒に選びたい。
