## 原則（ユーザー決裁）

> **プレイヤーが何かをやるたびに、その見返りとしてイベントが見られる。**

これを満たしているかで、足すものを決める。「合うゲートを探す」のではなく「足りない見返りを足す」。

---

## 1. 測って分かったこと（すべて実機実測）

### 1-1. 個別の見返りは、実は既にある

イベント台帳（`js/event_registry.js`）だけを見て「島側は空」と判断したのは**誤り**だった。
各画面が自前で個別の反応を返している。

| 行動 | 個別の見返り | どこ |
|---|---|---|
| ごはんを食べる | `react` ＋ `note`（実食コメント） | `js/ui_meta.js` |
| 服を買う／着替える | `DLG.OUTFIT[id]`（ミミの一言） | `js/data_dialogue.js` |
| スポット初訪問 | 到着ミニVN（ガイドとの掛け合い） | `js/ui_konron_map.js` |
| 写真を撮る | ガイドのヒント＋☆評価 | `js/photo_game.js` |
| ツリーのノード | `showLifeCutin`（枝色・フレーバー） | `js/ui_render.js` |
| 竜をスカウト | `_SCOUT_WIN_VOICE`（竜ごとの一言） | `js/ui_scout.js` |
| 習い事 | `levels[]`（段階ごとの文） | `js/ui_assets.js` |

★つまり **個別の層を1から書く必要はない**。

### 1-2. 空いているのは「節目」と「横断」

- **節目**（10品食べた／全スポット制覇／衣装◯着 …）＝ ほぼ無い
- **横断**＝ 島で何をしても、**顧問もSNSも反応しない**。食べても撮っても買っても、その世界の誰も知らないまま
- **物語の小イベント**が序盤に薄い（第3話直前で 3/16。13本が第4話以降に偏る）

### 1-3. レースだけ繰り返す層は、島の存在に気づけない

25レース走った時点のホームを実測：

| | |
|---|---|
| 行ける島スポット | **30/62（すべて未訪問）** |
| 食べ歩き | **0/44** |
| おでかけタブのドット | **無し** |
| 目標チップ | 1件のみ |

誘導の器（目標チップ・タブのドット）は既にあるのに、**未消化コンテンツと連動していない**。
紀行とメディアにはドットが点くのに、30箇所空いているおでかけには点かない。

### 1-4. 行動フックが無い

`runEventHooks` のフック一覧にレース系（`beforeRaceSelect` / `afterRaceResult` 等）は揃っているが、
**島側の行動フックが1つも無い**。`afterBet` / `duringRace` / `onStoryUnlock` は登録0本の空フック。

## 2. 設計

### A. 行動フックを足す（器）

`js/event_hooks.js` の `eventHooks` に追加。既存の `runEventHooks(hook, ctx)` にそのまま乗る。

| フック | 発火点 | ctx |
|---|---|---|
| `onMeal` | `eatMeal` 後 | `{ id, meal, tier, totalEaten }` |
| `onSpotVisit` | スポット初訪問 | `{ spotId, spot, area, totalSeen }` |
| `onPhoto` | 撮影の☆確定後 | `{ spotId, stars, masterpieces }` |
| `onOutfit` | 衣装の購入／獲得 | `{ id, outfit, totalOwned }` |
| `onLifeNode` | ノード取得 | `{ node, totalNodes, livingUp }` |
| `onLesson` | 習い事のレベルアップ | `{ id, skill, level }` |
| `onScout` | スカウト成立 | `{ dragonId, totalScouted }` |

★**既存の個別反応は消さない**。フックは「その上に世界の反応を重ねる」ためのもの。

### B. 節目イベント（初回＋節目）

各フックに「初回」と「節目」を置く。文面は既存の声表（顧問5人＋村人）に従う。

| 行動 | 初回 | 節目 |
|---|---|---|
| 食べる | サケ「まず食え」の回収 | 5品 / 10品 / 全ティア制覇 |
| 出かける | ガイドの歓迎 | 5箇所 / エリア制覇 / 全62箇所 |
| 撮る | 写真が「紀行」に載る | ★3初取得 / 10枚 / 幻の一枚 |
| 服 | サケの初陣祝い（既存） | 5着 / 10着 |
| ノード | 既存カットイン | 5 / 15 / 30（既存の `KURASHI_WATCH` を移設） |
| 習い事 | 師範との出会い | 各技能の最終段 |
| スカウト | 既存の一言 | 3頭 / 8頭（決戦の顔ぶれ） |

### C. 横断の見返り（★ここが本命）

**島でやったことに、レース場の側が反応する。** これが「世界が繋がっている」感を作る。

- **顧問が触れる**：次のレース選択で、ミズ「昨日、灯籠通りに居たでしょう。……あはん」等
  → 既存の `afterRaceSelect` フックに、島の実績を条件にしたイベントを足すだけ
- **SNSが拾う**：食べた品・撮った写真がタイムラインに出る（`sns.js` は既にデータ駆動）
- **紀行が記事にする**：既に `_kikoTodaysPost` が MEALS.react 等から日替わり記事を生成している
  → **既存の仕組みが強いので、条件を足すだけで横断が成立する**

### D. ツリー事前取得（解放前の獲得）

ユーザーの設計：**解放前でも、物語上ミミが実際に得たものは取得済みになる。
最初はフレーバーに見えて、ツリーが開いた瞬間に「あれは本物のノードだった、今度は狙って取れる」と反転する。**

- `onMeal` / `onSpotVisit` / `onOutfit` に相乗りさせる（新しい行動を作らない）
- **無償**で付与（`lifeTree.unlocked` に入れ、`lifeTree.bought` には入れない）
- 演出は既存の `showLifeCutin` を再利用
- 第3話でツリーを開くと「すでに ◯個 身につけている」＝反転が起きる

### E. ホームの誘導（★レースを繰り返す層へ）

**測定で分かった穴を塞ぐ。** 断定でなく「気配」を出す。

1. **タブのドットを未消化と連動**
   - 🏝おでかけ … 行けるのに未訪問のスポットがある
   - 🐲竜 … 図鑑に未確認の竜がいる／スカウトできる竜がいる
   - 🌳暮らし … 取れるノードがある／暮らしレベルが上がれる
2. **目標チップの回し方**：いまは1件固定。未消化の多い方向を優先して出す
3. **「何かあるようだ」の弱い誘導**：ホームのミミの吹き出しに、島の未消化を匂わせる一言を混ぜる
   （例：「そういえば、まだ行ってない通りがあるんだよね……」）
   → 既存の吹き出し機構に1行足すだけ。押し付けない
4. ★**FTUE保護は維持**：初出走前は何も出さない（`js/ui_home.js` の `completedRaces >= 1` ガード）

### F. 章ゲートを出来事に繋ぐ

B〜Dで出来事が増えたら、`docs/CHAPTER3_PROGRESSION_FIX.md` のゲート案を「数字」から「通った出来事」へ移す。
**先に出来事を作る。ゲートの繋ぎ替えは最後**（順序を逆にすると、繋ぐ先が無いまま数字をいじることになる）。

## 4. 実装の作法（「綺麗に」の中身）

- **既存の個別反応を壊さない**。フックは上に重ねるだけ
- **データ駆動**：イベントは `js/event_registry.js` に1本1オブジェクト。ロジックを書かない
- **門番**：未登場の顧問を喋らせない（`advisorMet` / `castNameSafe`・fail-closed）
- **1到着1モーダル**を守る（`progressionCheckOnHome` の作法）
- **表示専用**：着順・オッズ・配当・FinalPower には触れない
- 新しい正本を作らない（既存の `MEALS` / `KONRON_SPOTS` / `OUTFITS` を読むだけ）

## R4 実装記録（2026-08-01・完了）

**島でやったことに、レース場の側が反応する。** 実装は2層。

### ① 顧問が触れる（`js/event_registry.js` 末尾・8本）
`afterRaceSelect` に `once:true` で登録。**実名で言う**のが肝で、`text` に関数を渡して
発火時に state から場所名・料理名を引く（`_r4LastSpotName()` 等）。

| id | 条件 | 話者 |
|---|---|---|
| `x_mizu_saw_you_out` | スポット3か所＋名前が引ける | ミズ |
| `x_sumika_island_walker` | スポット15か所 | スミカ |
| `x_sake_you_ate` | 食べ歩き5品＋名前が引ける | サケ |
| `x_makura_food_content` | 食べ歩き15品 | マクラ |
| `x_makura_saw_photo` | ★3写真1枚 | マクラ |
| `x_mizu_stable_grows` | 龍舎2頭 | ミズ |
| `x_sumika_dressed_up` | 衣装3着 | スミカ |
| `x_sake_life_settled` | ツリー8ノード | サケ |

**発火の実測**：`runEventHooks` は `vnBudget = 1`＝**1フックにつき喋るイベントは1本だけ**
（`js/event_hooks.js`）。同一優先度では登録順が勝つので、R4は毎レース1本ずつ順に出る＝
まとめて降ってこない。優先度は 0 のまま＝地域初訪問の説明（同じく0・先に登録）が先に出て、
それが済んでからR4が出る。この順序は意図どおりなので priority は足していない。

### ② SNSが拾う（`js/sns.js` `SNS_POSTS` 末尾・5本）
既存の `p_walker`「島を歩く人」/ `p_gourmet`「うまそうに食う子」は**匿名の一般論**だった。
R4で足したのは**固有名を出す投稿**（`p_x_spot` / `p_x_meal` / `p_x_photo` / `p_x_stable` / `p_x_walker20`）。

- `unlock()` で**名前が引けることまで**確かめる＝穴あき投稿（「、うまそうに食う」）を出さない。
- 文面は「最近／このごろ」＝**現在進行の観測**にする。`text` は描画のたびに評価されるので、
  「〜に行った」と過去形にすると次の外出で**過去の投稿が書き換わって**見える。
- 早い3本は `unlockDelayDay` で1日ずらす（既存の還流投稿と同じ作法）。

### ⚠ 途中で見つけた事故（記録）
`POST_TEMPLATES`（ミミが自分で投稿するテンプレ・13件）は **`postTemplates()` が
どこからも呼ばれておらず、全部が死にデータ**。R4を最初ここへ足してしまい、実機で
タイムラインに出ないことで気づいた。**SNSに何か足すときは `timelinePosts()` から
辿れるか（＝`SNS_DAILY` か `SNS_POSTS`）を先に確かめること。**

### 検証（実機・DOM実測）
- 実経路 `renderRaceDetail(race)` で `x_mizu_saw_you_out` が発火し、立ち絵つきで
  ミズ・アオラ「昨日、ウロコトロ温泉郷に居たでしょう。……見てましたよ、あはん。」を確認。
- `timelinePosts()` に4本が実名で出ることを確認（龍舎0頭の `p_x_stable` は正しく非表示）。
- ★Browserペインのスクショが古い描画のまま止まるため、目視ではなく **DOM実測**で確認した
  （[[browser-pane-hidden-shot-server]] と同じ症状）。
- テスト汚染は `resetGame()` で復旧済み（spots 0 / meals 0 / coins 1000 / x_フラグ0）。

## P-8 ポロのグルメレース ブラッシュアップ（2026-08-01・完了）

### いちばん大きかった問題
**専用アートが納品済みなのに、ゲームは絵文字を描いていた。**
`images/poro_race/` に走る/跳ぶ/転ぶポロ・食べ物5種・背景3枚（夜市/果樹園/食糧庫）がある。
作り込みより先にこれを結線した。背景は距離 5200 ごとに切り替わり、終盤8%でクロスフェード。
描画は必ず高さ基準で比率を保つ（`pgDrawImg`・[[character-aspect-ratio-immutable]]）。

### 手触り（跳ぶゲームの土台）
- **コヨーテタイム 90ms**／**ジャンプバッファ 120ms**。無いと「押したのに跳ばない」が出る。実機で両方の発火を確認。
- **出現を決定的な剰余からPRNGへ**。旧実装は `roll = (dist + score*7 + items.length*13) % 100`＝
  **スコアで地形が変わる**という妙な挙動だった（腕が上がるほど別のゲームになる）。
- **演出の乱数は `Math.random`、ゲームの乱数は `pgRnd`**。演出で `pgRnd` を消費すると
  **描いたフレーム数で地形が変わる**＝端末の速さで難易度が動く。分離は必須。
- **避けられない配置を作らない**：滞空の実測は 620ms。640ms×1.35 の間隔が空くまで障害を置かない。

### 実測（この数字が判断の根拠）
| 先読み距離 | 最善プレイヤーの平均被弾／走 |
|---|---|
| 40px | 4.88 |
| **60px** | **0.13** |
| 100px | 6.88 |
| 150px | 10.50 |

→ **配置は理不尽ではない**（60pxで踏み切れば当たらない）。難所は配置ではなく**踏切りのタイミング**で、
早すぎると障害の上に着地する。runnerとして正しい難しさなので、ここは調整していない。

### 演出（すべて純表示・スコアと当たり判定は不変）
取得パーティクル／スコアポップ（紫の果実は大きく）／被弾で画面ゆれ／5コンボごとの発光／
ダッシュ中のスピード線／走りの上下・転倒の傾き／背景の床と地面帯をグラデで繋ぐ。

### 検証
30秒フル走を毎フレーム描画つきで通し（1800フレーム・例外なし）、結果画面→ランクB→ごほうび解放まで確認。
テスト汚染は `resetGame()` で復旧済み。
