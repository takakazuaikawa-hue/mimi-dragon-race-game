# 画面サイズの単一ルール（正本） — 聖龍爆走録ミミ

このゲームは**スマホでもPCでも常に縦画面**（YouTube Shorts / TikTok と同じ考え方）。
新しい画面・演出・CSS・背景画像を足す前に必ずここを読む。数値は**ここだけが正**＝他ドキュメント（`RESPONSIVE_GUARDRAILS.md`）やCSSコメントはここを指す。
[[race-math-immutable]] とは無関係（レイアウト/CSSのみ）。

---

## 0. 考え方（なぜ縦固定か）

**スマホは元から縦。直したいのはPC（横長ディスプレイ）でどう見せるか**、その一点。
YouTube Shorts/TikTok が横長環境（PCブラウザ）でどう振る舞うか調べた結論：
- 正の縦横比＝9:16。**PCでは、コンテンツを横に潰さず、縦のまま中央へ配置し左右を余白で埋める**（ピラーボックス）。
- セーフゾーン＝プラットフォームUIに隠れる余白を避ける発想。このゲームでは"上=ヘッダー/戻る"「下=常設ドック(レースへ進む/ナビ)」に対応。

このゲームはDOMアプリだが、**PC枠は実際のShorts動画エリア(9:16厳密固定)に倣い、縦横比そのものを固定する**（2026-07決定）。
- 横幅は**470px**（既存資産のvh基準表示に合わせて確定済み。変更する場合はホーム立ち絵のvh計算を再検証すること＝安易に変えない）。
- **PC枠（`≥540px`）では `body` 自体を `aspect-ratio: 9/16` に厳密固定**（470×836px）。極端に縦長のPC窓では、本物のShortsがPCで動画を伸ばさず余白で埋めるのと同じ発想で、**bodyの上下にも世界観アンビエントのレターボックスができる**（左右だけでなく上下も）。
- スマホ実機（`<540px`）は今まで通り**アスペクト固定なし**（`dvh`で可変・端末の実画面いっぱい＝Shorts本来の「画面いっぱい・比率は端末依存」に対応）。

※スマホを横向きに**回転させること自体はこのゲームの対象外**（想定していない）。既存コードには「回転してもUIが詰まない」ための保険（低い高さでのスクロール解放＋タッチ端末への「縦にしてね」案内）が入っているが、これは事故防止の保険であって、本ルールが積極的に設計している対象ではない。

## 1. ★今回の本題：背景画像が画面サイズと合っていなかった問題（診断と修正）

### 症状
ホーム背景（`images/homebg/*.webp`）は横長の写真（16:9）を `object-fit:cover` で縦長の画面に敷いている。
**画面のアスペクト比によって、写真の構図の主役（右1/3に配置された火山）が丸ごと切り落とされて見えなくなる**。

### 原因（実測で確認）
`.hl-bg-img` は `object-position` が既定値（中央50%）のまま固定されていた。縦長の画面幅では
横方向の**中央付近28%程度しか表示されない**（cover計算上、残り72%は左右に切り捨てられる）。
写真の火山は横位置70〜80%あたりにあるため、**中央基準の crop では最初から視野の外**。

**実測比較（375×812、同一画像onsen）**：
- `object-position: 50% 50%`（修正前）→ 空と海だけで火山が完全に消える。
- `object-position: 79% 50%`（修正後）→ 火山がしっかり画面内に入る。

### 修正内容（実装済み）
6ロケーションの画像を実際に確認し、火山（または自宅の窓越しの火山）の実際の横位置を計測して
`focusX`（画像内の見せたい横位置・左端0〜右端1）を実測値でデータに追加。
`js/ui_home.js` `HOME_BGS` の各エントリに `focusX` を持たせ、読み込み時に
`im.style.objectPosition = (focusX*100) + "% 50%"` を設定する（**縦持ちsvgデモ(`portrait:true`)は対象外＝素直なcoverのまま**）。

| ロケーション | focusX（実測） |
|---|---|
| balcony | 0.77 |
| beach | 0.80 |
| market | 0.71 |
| onsen | 0.79 |
| stable | 0.78 |
| mall | 0.71 |
| myroom（自宅・全段共通） | 0.80（t0/t3の実測平均・全段の実測ではない） |

`object-position` はブラウザ標準機能なので、画像の端を超えて透明/黒帯が出ることは無い（自動クランプ）。
新しい背景画像を追加する時は、**実際にその画像を開いて火山（主役）の横位置を目視で測り、`focusX` に入れる**こと
（"だいたい0.8だろう"と決め打ちしない＝実測が今回の教訓）。

### 縦位置（floor）との関係
既存の `floorUsed`（接地ライン・上端からの比率）による縦位置補正はそのまま維持。
`focusX`（横）と`floorUsed`（縦）は独立した別軸の補正＝両方があって初めて「主役が画面内・足がドックに合う」が両立する。

`≥540px` で 470px 中央カラム＋左右アンビエント。**幅だけで判定**。既存実装は実測済みで健全

## 4. 参照実装

- 背景の横位置補正：`js/ui_home.js` `HOME_BGS` の `focusX` ＋ `im.style.objectPosition`（本書§1）。
- 背景の縦位置補正（既存）：`js/ui_home.js` `calibrate()`（`floorUsed`・`docs/HOME_BG_SPEC.md`）。
- **PCフレーム（9:16厳密固定＋fit-height・2026-07実装）**：`style.css` `@media (min-width: 540px)`。
  - `html`＝`display:flex;align-items:center;justify-content:center`（bodyを縦横中央へ）＋`::before/::after`が世界観アンビエント（レターボックス全体を埋める・home/title含め常時）。
  - `body`＝`max-width: min(470px, calc(100dvh * 9 / 16));aspect-ratio:9/16;overflow:hidden;transform:translateZ(0)`。
    **★fit-height**：枠の高さがウィンドウ実高さを超える場合は本物のShorts同様“端末ごと縮む”＝低いノートPC窓でも
    ページスクロールが出ない（実測：1280×800→450×800／1366×768→432×768、いずれもスクロール0・縦横中央）。
    縦長窓では470×836にキャップし上下レターボックス（700×2000→上582px）。旧「既知の残課題（低い窓で数十pxスクロール）」はこれで解消。
    （＝**containing block化**。`document.body.appendChild`のモーダル/演出/音量ボタン等が個別修正なしで枠内へ収まる）。
    `min-height:0`で基本ルールの`min-height:100dvh`を打ち消す（無いとaspect-ratioが無視される＝実測で発覚した罠）。
  - `#header`＝`flex:none;max-width:100%`／`#app`＝`flex:1 1 auto;overflow-y:auto;max-width:100%`（内部だけスクロール）。
    **★max-widthをnoneにしない**：noneだと横カルーセル等の固有幅で#appが数千pxに膨張し中身が右へ切れて見える
    （観光`.kt-rail`で実測7523px）。`100%`＝枠幅にクランプし、広い子は各自の`overflow-x`で内部スクロールに収まる。
  - **既知の副作用と対処**：画面遷移アニメーション（`#app.nav-fwd > *`等）が`transform`を`fill-mode:both`で残すと、`position:sticky`な子要素（`.rs-ctrl`等）の基準計算が壊れる（Chromium系の既知の癖）。`both`→`backwards`に変更して解消済み。
  - **計測の作法（devcheck）**：入場アニメ(translateX)の途中で測ると全画面が“右に+18px あふれ”に見える誤検出が出る。
    さらにバックグラウンドタブではCSSアニメ/rAFがスロットルされ「待っても終わらない」。よって
    `responsiveSelfCheckAll` は**finiteアニメを`finish()`で終端へ強制送りしてから測る**（rAF不使用）。
  - **検証済みマトリクス（2026-07-02・全27画面✅）**：320×700／390×844／1280×800／1366×768／700×2000。
- 運用チェックリスト：`docs/RESPONSIVE_GUARDRAILS.md`。

## 5. 新しい背景画像を追加する時のチェック
1. 画像を実際に開いて、主役（火山など）の横位置を目視で測る→ `focusX` に実測値を入れる。
2. `?go=home` を 320 / 375 / 470（フレーム）幅あたりで見て、主役が画面内に入るか確認。
3. 昼夜で構図が大きく違う画像なら `focusXNight` を別途追加できる（`floorDay`/`floorNight`と同じパターン）。
