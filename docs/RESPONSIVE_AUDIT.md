## 結論（先に要点）
土台は**思っていたより健全**：横スクロール無し・canvasはDPR対応・safe-area対応・タップ最適化済・主要inputは16px以上（iOSズーム無し）・PCの470px固定枠も設計通り中央寄せで機能。
ただし**「縦持ち前提の作り」が抜け道**になっていて、特に**横向き（landscape）でホーム下部が完全に隠れて操作不能**になるのが最大の穴。下にズレ幅の大きい順で列挙。

## 🔴 High（実害・最優先）

### H1. 横向き（landscape）でホーム下部が消える＝レースボタン/メニューに到達不能
- **実測**：740×360 で `.hl` の高さ=486px に対しビューポート=360px。`body.home-mode` が `position:fixed; inset:0; height:100%`（[style.css:2087](../style.css:2087)）で**ページがそもそもスクロールしない**ため、はみ出した下部（`hl-dock` / `hl-cmbar`(コメント) / `hl-likebtn` / **`hl-race`=レースへ進む** / **`hl-rail`=ナビメニュー**）が**クリップされ操作できない**。縦持ち 375×812 では全要素が収まり完璧（＝横向き固有）。
- **原因**：ホームは「TikTok風ノースクロール全画面」を縦持ち前提で固定設計（`.hl { min-height: calc(100dvh - 30px) }` [style.css:3183](../style.css:3183)）。**orientation（向き）対応は全くの未実装**（コード内に landscape/orientation 分岐なし）。
- **対処案**：(a) `orientation: landscape` かつ低い高さの時だけ「📱 縦にしてね」オーバーレイを出す（最小工数・確実）。(b) 短い高さでは home-mode の固定解除＋スクロール許可＋立ち絵を縮める compact レイアウト。→ **(a)+(b)併用**を推奨（基本は縦推奨、それでも横で触れるよう保険）。

## 🟡 Medium

### M1. 中間幅（471–699px）が“どっちつかず”
- **実測**：557px でホームの縦長配信レイアウトが広い枠に浮いて、左端の流れるコメントが立ち絵裏に隠れ気味。情報密度の高い画面はテキスト行が間延び。
- **原因**：PCの470px枠は **`@media (min-width:700px)`** でしか効かない（[style.css:1610](../style.css:1610)）。一方デフォルトは `#app { max-width:720px }`（[style.css:1112](../style.css:1112)）。**471〜699px の帯はフレーム無しで最大~660pxまで伸びる**。該当：タブレット縦、iPad SplitView、PCウィンドウ縮小、大型スマホ横（横はH1優先）。
- **対処案**：枠適用の閾値を下げる（例 `min-width:520px` で 470枠を効かせる）。閾値はブレークポイント統一（L2）と合わせて決める。

### M2. 「村レベルが ？ に上がりました」＝レベル値が出ないフォールバック
- **実測**：ホーム遷移時にVNで表示確認。
- **原因**：[event_registry.js:327](../js/event_registry.js:327) が `ctx.newLevel` 未指定時に `"?"` を出す。発火側が `newLevel` を渡していない経路がある（当方の高速ナビでも誘発し得るが、フォールバックが本番でプレイヤーに見える可能性）。
- **対処案**：発火元で `newLevel` を必ず渡す／渡せない時は文面を「村レベルが上がりました」に変える（？を出さない）。要・発火経路確認。

### M3. ホーム立ち絵が2枚見える瞬間（背景ミミ＋VSセリフ立ち絵）
- **実測**：557px で 背景の薄いミミ立ち絵 + 前面のスミカ(VN)立ち絵が重なって見え、やや雑然。
- **メモ**：[[home-tiktok-live]] に「ホームでミミVN立ち絵は出さない（二重防止）」。今回はミミ＝配信者(背景)／スミカ＝VNゲスト なので二重Mimiではないが、重なり時の見栄えは要調整（前面VN時は背景立ち絵を更に沈める等）。

## 🟢 Low / Polish（保守性・体感の底上げ）

### L1. `body { min-height: 100vh }` だけ dvh/svh 化されていない
- [style.css:46](../style.css:46) は `100vh`。他は `100dvh`/`100svh` を使用（例 [3183](../style.css:3183) [4653](../style.css:4653)）。iOSでURLバー分のズレ要因。`100dvh` に統一推奨（低リスク）。

### L2. ブレークポイントが散在（380/420/480/520/560/620/680/700/max-height:680）
- 体系が無く、同種調整が別閾値に散る＝保守性低下。**2〜3段の標準ブレークポイント**（例：≤480 小スマホ / ≤700 スマホ・タブレット / ≥700 PC枠 ＋ landscape）に寄せ、CSS変数化を検討。ユーザー要望の「エンジン化/整理」に合致。

### L3. 視線パララックス（_mimiGaze）が mousemove 依存＝タッチで効かない
- [ui_home.js:375](../js/ui_home.js:375) は `e.clientX/clientY`。スマホ（タッチ）では発火せず立ち絵の視線追従が出ない（PC限定の隠し演出化）。装飾なので低優先。任意で `deviceorientation` 等の代替。

### L4. PCワイドで非ホーム画面の左右が単色グラデで空く
- ≥700px は 470px枠＋`--bg-world` の地。**設計通り（タスク#6「PC固定枠」）**だが、広いモニタでは左右が寂しい。ホームのような全幅アンビエント背景/装飾を非ホームにも薄く敷くと“作り込み感”が出る（任意）。

### L5. タイトルも `position:fixed`（横向きで下部ボタンが中央アートに被る可能性）
- `.sv-hint`/開始ボタンは `bottom: max(20px, safe-area)` の絶対配置（[style.css:2219](../style.css:2219)）＝下端に残るのでH1ほど致命的ではないが、極端に低い横向きで中央タイトルと重なる懸念。H1対処（縦推奨オーバーレイ）に相乗りで解消可。

## ✅ 検証済みの“非問題”（直す必要なし・無駄打ち防止）
- **横スクロール**：360px 静定後 overflow=0（先に見えた18pxは画面遷移アニメ scrInFwd の一時値）。
- **canvas**：DPR対応でぼやけない（[race_canvas.js:1140-1169](../js/race_canvas.js)）。
- **safe-area**：ノッチ/ホームバー対応済（header/タイトル/下部ドック等で `env(safe-area-inset-*)`）。
- **タップ**：`touch-action:manipulation`＋`-webkit-tap-highlight-color:transparent`＋`overscroll-behavior:none`（[style.css:33-38](../style.css:33)）＝300ms遅延/ダブルタップズーム/引っ張り更新を抑止。
- **input自動ズーム**：主要入力 `.wager-big`=26px（[style.css:2586](../style.css:2586)）＝16px以上でiOSズーム無し。`.hl-cminput`(12px)は入力欄ではなくタップ起動のダミー。
- **PCの470px枠**：1280pxで `#app` x=405 / margin-left auto / 中央470px＋背景1508pxフルブリードを実測。設計通り。

## 推奨対応順
1. **H1（横向き）** … 縦推奨オーバーレイ＋（可能なら）短高さ時スクロール解放。体感最大。
2. **M2（？レベル）** … 小修正、見栄えバグ潰し。
3. **L1（dvh統一）＋ M1/L2（ブレークポイント整理＆470枠閾値）** … まとめてレスポンシブ基盤を整える。
4. **M3 / L3 / L4 / L5** … 仕上げポリッシュ。

> 計測手順：プレビューを各サイズに `preview_resize` → `goto(screen)` → 要素の `getBoundingClientRect()` で overflow/clip を実測（スクショは本プレビュー窓が約557px幅のため、それ超の幅では縮小されて誤認するので**計測値を正**とする）。
