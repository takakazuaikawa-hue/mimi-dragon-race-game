# 神眼・公正な予想特集の独立試作

## 採用判断

競走を編集するゲームは取り下げる。ミミが編集するのは、自分の紀行に載せる **3 枚の予想**。島で整えた港と市場、迎えて観察してきた竜の知識を持ち込み、公正な競走の結果を待つ。

セレスティアの 1 着予言は最後まで正しい。ミミが目指すのは「予言を外させる」「同着を作る」ことではなく、取材に基づく予想を届け、島の一日を支えること。引き分けは二人が認める物語上の結末であり、着順の同着ではない。

本試作の成功目標は **3 枚中 2 枚以上的中、かつ一日の総運営収支が 0 コイン以上**。神眼が公開した 1 着の複勝だけでは前者を満たさない。全て外して主催者だけ儲かる紙面も成功しない。

## 公正性の境界

- プレイヤーの全操作は、競走の seed・出走竜・能力・走り・着順・タイムを変えない。走る相手への依頼、負ける指示、並走指定、能力編集、狙った同着を一切含めない。
- `getRace(scenarioId)` は準備・紙面・財布を引数に取らない。`resolve` も同じ結果を読むだけ。
- 港は読者が来る条件、市場は商業収入、取材記録は予想の選択肢にのみ作用する。スカウトした竜を出走させたり、未スカウトの竜を欠場させたりしない。
- 単勝・複勝・ワイドは独立したプール。複勝やワイドの記事で単勝の配当を上げることはない。単勝は全ケースで売上 1,000・払戻 1,000・運営取り分 0 のまま。
- 記事は観察事実と予想を区別する。ミミは的中・利益を保証しない。読者の購入も記事の指示どおりにはならない。

## 最初の 3 分

1. **0:00–0:30、島を見る。** 港の修繕と市場の灯りを選ぶ。デモの 600 コインから 120・150 が減り、残り 330 が見える。港は人を増やし、市場は賭け以外の収入を生む。準備済みモードなら、この状態から始まる。
2. **0:30–1:30、取材した竜を読む。** 大判の竜アートから候補を開き、コース条件と観察メモを見る。「登りに強いフガクなら 2 着も狙える」「終盤型の組み合わせをワイドで読む」など、自分の根拠を持って 3 枚を紙面へ置く。置くたび客の反応、票の集中、的中時の払戻範囲、一日収支の範囲が変わる。
3. **1:30–2:00、届ける読者を迷う。** 01 は読みを信じる客、02 は配当を探して比較買いする客、03 は今日来た竜のファン。同じ予想でも、掲載先で来る人数と票の集中率が変わる。読みに自信のある竜を強く押すか、薄い組合せを紹介するか、応援客へ届けるか。的中への自信と島の収支を同時に見る。
4. **2:00–3:00、発行して結果を見る。** 公正なレースを見届け、各記事の的中、読者の払戻、券種別の運営取り分、市場収入を答え合わせする。失敗しても本編コインを消費しない。同じ競走で紙面だけを変えて比較でき、次のコースでは別の知識を使う。

視覚表現はこの操作から導く。竜の写真・肖像を選んで紙面に載せ、客の読み方が変わり、最後に記事へ結果の印が入る。金枠・宝玉で数値操作を着飾る方向には戻さない。競走再生は結果の確認であり主操作を奪わない。区間データがない試作では、追い抜きのドラマを勝手に捏造せず、タイムに基づく簡略再生と明示する。

## 最小モデルと限界

競走は 3 コースの **固定検証用レース記録**。本編の計算式を移植したシミュレーションではなく、毎回新しい乱数で引き直すゲームでもない。着順・タイムはコースごとに固定し、竜の既存の特徴に沿う状況を用意している。本編の競走式は変更していない。公開前には 1 着予言と条件だけを見せ、2 着以降を UI に出さない。ローカル JS のデータは解析可能であり、秘密をサーバーで保護する製品仕様ではない。

複勝 8 枚、ワイド 6 枚の計 14 候補から異なる 3 枚を選ぶ。複勝は 2 着以内、ワイドは 2 頭とも 3 着以内。3 枠の基本掲載倍率は 1 / 0.82 / 0.64 に、公開された読者の関心を掛ける。01 は複勝を読む客が多く、記事の予想へ 78% の票が向かう。02 は発行前の票が薄い選択肢に関心があり、50% は別の予想も比較して買う。03 はコースごとに来訪するファンの構成で届く人数が変わり、90% が記事の予想へ集まる。これらは試作用の購買仮説。関心の強さは的中確率ではなく、ファンの多い竜を必ず上位へ入れてはいない。

払戻は試作専用の小さい架空モデル: プール売上の 80% を的中選択肢へ均等配分し、各的中票は最低 1.0 倍を返す。複勝の 2 枠、ワイドの 3 組への集中によって、最低払戻の補填で取り分が減る場合がある。発行前からある基礎票は単勝 1,000・複勝 2,040・ワイド 2,300。複勝のライオウ、ワイドのライオウ×ポロなどへ既に人気が偏っている。残った収支に市場収入を足し、営業規模に対応した運営費 760 を引く。本編の最低オッズ（単勝 1.3／複勝 1.1／ワイド 1.3）や計算式とは異なる。小数は表示用に 2 桁へ丸める。初版の薄いプールと運営費 300、読者枠改修時の 800 を経て、準備条件別の監査から 760 に調整した。払戻率・最低払戻には上乗せしていない。

収支見込みと的中時オッズは、ライオウ以外の 2・3 着の全 42 通りを列挙した最小・最大。確率分布や期待値ではない。実際の隠れた着順は使っていない。記事の魅力、客の反応、2 枚的中という基準はプレイテスト用の仮説であり、人間が面白いと感じることまで証明するものではない。

## API 契約

ファイルはブラウザで `globalThis.ShinganPrototype`、Node で CommonJS export。DOM・本編 globals・通信・時計・localStorage に依存しない純粋関数群。

| API | 契約 |
| --- | --- |
| `createState(mode='arrival', scenarioId='coast')` | 新規デモ状態。mode は `arrival` / `prepared`、scenarioId は `coast` / `gorge` / `sky`。`{version,scenarioId,coins,prepared:{harbor,market,scout},scouted,log}`。 |
| `prepare(state, action)` | action は `harbor` / `market` / `scout`。新しい状態を返し、入力を変更しない。重複準備は二重請求しない。未知 action・残高不足は例外。 |
| `getView(state)` | `{scenario,scenarios,editorSlots,dragons,offers,preparations,coins}`。scenario に公開条件・`oracleWinner`・`fanInterest:[{id,name,interest}]`、editorSlots に `{id,title,description}`、offers に `id,type,ids,title,reason,risk,locked,image,key`。`risk` は日本語の説明文字列。着順を含めない。 |
| `preview(state, plan)` | plan は最大 3 要素の配列。候補 ID または空欄を表す `null` を指定し、位置が読者枠を表す。例 `[null,'p_fugaku',null]` は 02 の配当読者へだけ掲載。空欄を前詰めしない。非 null の重複・未知 ID・未取材を拒否。無効なら `{valid:false,errors}`、有効なら下記の見込みを返す。 |
| `resolve(state, plan)` | 3 枚必須。preview の出力に `race,settlement,predictions,hits,operatingProfit,balanceAfter,success,oracleCorrect,feedback` を加える。試行は状態・財布を変更しない。 |
| `getRace(scenarioId)` | `{seed,order,oracleWinner,rows:[{id,name,rank,time,gap}]}`。time/gap は秒、1 着は 120 秒。区間 trace はない。UI は発行後に取得する。 |
| `enumeratePlans(state)` | 解放済み候補から全ての異なる 3 枚を順序付きで列挙する。検証用。UI の自動解答には使わない。 |
| `settlePool(stakes, winningKeys)` | 単独プールの純粋計算。テスト・会計確認用。 |

preview のフィールド:

```js
{
  valid: true, errors: [],
  pools: {
    win:   {total, stakes, concentration, estimatedNet: {min, max}},
    place: {total, stakes, concentration, estimatedNet: {min, max}},
    wide:  {total, stakes, concentration, estimatedNet: {min, max}}
  },
  audience: {readers, newStake, harborOpen},
  features: [{id, slot, type, ids, title, key, stake, directedStake,
              readers, audienceLabel, reaction, odds: {min, max}}],
  commerceIncome, operatingCost, estimatedProfit: {min, max}, warnings
}
```

- `stake` は記事に反応した客がその券種に購入する合計コイン、`directedStake` はそのうち記事に書かれた予想へ買った分。残りは同じプールの別の選択へ向かう。
- `features.odds` は **的中した場合** の倍率範囲。外れの 0 は範囲に含めない。
- `features` は掲載記事のみを返し、`slot` は元の配列位置を保つ。UI は `preview` / `resolve` に null を含む紙面をそのまま渡す。記事数を数えるために除いた空欄を、計算用配列にも適用しない。`resolve` は 3 枠が全て埋まるまで発行を拒否する。
- `predictions` は `{id,type,ids,title,hit,stake,payout,odds}`。ここで stake は `directedStake`、payout はその客全員への払戻合計。ミミの個人支出・収入と表示しない。
- `settlement.{win,place,wide}` は `{total,payout,houseNet,distributable,refundSupport,payouts,odds}`。売上と払戻の差が `houseNet`。`distributable` は 80% の配分原資、`refundSupport` は最低払戻を支える補填額。通常の原資と補填を分け、的中したのに運営が赤字になる理由を示す。
- `balanceAfter` は準備後のデモ残高に一日収支を加えた参考値。これを次の試行の state.coins に代入しない。失敗や比較による繰り返し請求はない。

## 回帰検証と採否

実行: `rtk proxy node tools/check_shingan_prototype.cjs`。

検証対象は全 3 コース × 準備の全 8 組合せ × その時点の全合法紙面。準備済みでは 14 × 13 × 12 = 2,184 通り / コース。隠れた着順だけを反転したエンジンも別 VM で作り、全紙面の公開情報・予測が変わらないことを比較する。

読者枠改修と営業費 760 への調整後、準備済み・標準表紙での列挙結果:

| コース | 成功する掲載順 | 順序を除く成功 3 枚組 | 2 枚以上当たるが赤字 |
| --- | ---: | ---: | ---: |
| 海風 | 291 | 54 | 93 |
| 峡谷 | 235 | 55 | 365 |
| 雲上 | 164 | 29 | 40 |

全コース共通で成功する固定 3 枚組は 0。どのコースにも、神眼の複勝を使わない成功紙面、3 枚とも的中する成功紙面、異なる組合せの成功紙面がある。全ての成功に共通する必須カードもない。市場なしの港＋取材だけでも海風 190・峡谷 118・雲上 112 通り成功し、そのうち全的中も 7・4・2 通りある。これらは用意した 3 レースでの性質であり、あらゆる将来レースでのバランス保証ではない。

人が触る検証では、最初の 3 分で以下を観察する。

- 竜や条件のどの記述を根拠に 1 枚を選んだか、自分の言葉で説明できるか。
- 発行前に「この組が来るか」を気にして結果を待つか。客数の大きいカードを並べるだけになっていないか。
- 外れ・集中・準備不足のどれを直そうとするか判断でき、2 回目に自分で紙面を変えたくなるか。
- 準備済みと未準備を比べ、「既に島を整え、竜を知ってきた」効用が伝わるか。
- 別コースで同じ紙面を惰性で出さず、条件を読み直すか。

説明を読まないと何も選べない、収支の最大化だけを見る、同じ競走で答えを覚えただけで満足が終わる場合は、この案も採用しない。固定レースを大量追加して先に規模を広げず、情報の提示量・カードを置く反応・結果の答え合わせを小さく再調整する。

## 実物レビュー・2026-11-17

**独立プレイテスト試作として採用する。** 修正後の画面と UI コードで、準備→紙面への配置→読者と的中時倍率の反応→公正な着順と記事の答え合わせ→差し替えの流れを確認した。カード上からの縦移動、空き枠と掲載順の計算の一致、選択記事の見込みの常時表示、上位 3 頭と記事ごとの実着順表示を改善済み。実装担当によるブラウザ検証では、375 / 360 / 470 px、タップ・縦横スワイプ・ドラッグ・キーボード・動きを減らす設定、および本編 storage 不変を確認している。設計レビューではスクリーンショットとコードを確認し、ブラウザ操作を独立して再実行したものではない。

この採用は本編への統合、商用品質の完成、楽しさの実証を意味しない。3 本の固定レースは答えを覚えられ、一定速度の再生から竜の区間ごとの駆け引きを検証することもできない。準備は本編の長い経済救済・交流を短縮しており、その積み重ねの感情まで再現してはいない。客の反応と払戻は試作用の架空モデルである。次に判断するのは機能の追加量ではなく、初見の人が根拠を持って選び、結果を待ち、自分からもう一枚を変えたくなるかである。

### 実操作による再評価と読者枠改修

上記の画面レビュー後、設計担当 Astra が Playwright / Edge、375×812 で URL を実際に操作した。エンジンやソースから答えを取得せず、準備前→失敗→港・市場の購入→8 頭の取材記録を開く→紙面差し替え→再発行→別コースを実行。ただし設計者は既に固定結果を知っており、完全初見ではない。別の Astra にもソース未参照で独立プレイを依頼し、両者を人間プレイヤーの評価とは区別した。

初版の実操作では、未準備のライオウ複勝／ポロ複勝／ライオウ×ポロが 1 枚的中・−114。準備後にポロ枠をフガクへ、ワイドをフガク×グレイズへ変えると全的中・+44。しかし難しいワイドが 166 コイン→166 コインの元返しだった。峡谷ではヨミ複勝／ライオウ×ヨミ／ヨミ×ポロが全的中・+62.3 だが、2 枚は元返し。別コース初手の 14 候補も全て 1 倍だった。独立評価者も「確定 1 着＋条件に合う相方の複勝＋同じ組のワイド」が一つの読みへ収束し、全的中のまま紙面を替えて赤字になった時に説明が不十分と報告した。

この結果から、初版は動作する試作としては成立するが、予想の期待と再挑戦の動機は不足すると再判定。公正な競走と本編分離を維持したまま、上記の基礎票・3 読者枠・営業費へ改修した。初手の未知竜複勝は約 1.9〜2.6 倍、未知 2 頭ワイドは約 2.2〜2.8 倍の見込みとなる一方、確定ライオウ複勝と人気集中したライオウ×ポロは 1 倍を保つ。全的中でも赤字になる選択は残し、その最低払戻補填と前回との差を説明する。準備をわざと不足させる新しい制限や、相関する予想を禁止する条件は追加していない。

「3 枚が同じ竜の読みへ依存する」性質は、相関を明示し、届ける読者と収支を変えることで判断材料にする。相関の表示や数値の組合せ検証だけで、長期的に深いゲームになったとは結論しない。改修後も同じ型の紙面を機械的に置くだけなら、次の採用判断で核そのものを見直す。

改修後の採否は **独立した短時間のプレイテスト版として採用**。予想を当てることと届け先を考えることを、実際の操作で比較できる段階になった。独立評価者にも、初版より自分の仮説で再試行する理由が生まれた。ただしこれは AI 2 名の実操作記録であり、人間テストの証明ではない。

独立プレイでは、記事の削除で後続を前詰めすると、他の記事まで違う読者枠へ移る問題も見つかった。読者枠は固有の役割になったため、API を nullable 3 枠へ変更し、削除は選んだ枠だけ空欄にする。03 だけの配置、01 を消した後の 02/03 の属性・購入量の保持、空欄を挟む重複や未取材の拒否、未完成紙面の発行拒否を回帰検証に加えた。

残題は二つ。第一に、固定 3 レースの結果は覚えられるため、同コース再試行は「新しい予想」ではなく既知の競走を使う紙面比較と明示する。第二に、人気竜の外れ記事を載せる方が運営収支を増やせる場合がある。全的中でも成功する紙面と複数の選択は残っており、外れ記事は必須ではないが、この誘因は消えていない。収支最大の紙面だけを最良と表彰せず、外れと読者の払戻も表示する。初回の本気の予想で人が何を選び、何を後悔するかを次の評価点とする。

## 島の記憶を結ぶ、次の小さい縦切り

追加依頼の中心は、アイテムや料理を増やすことよりも、出会い・持ち物・学んだ理論が最後に自分の読みへつながる「総決算」の重み。島へ 3 つの任意の寄り道を加え、一つの記憶を表紙に、記憶と理論の組合せを各予想の根拠として持ち込む。全地点の訪問・全理論の回収・衣装の購入は成功条件にしない。

表紙で招く顔ぶれは **1 組だけ**。いずれもファン関心の 1.6 / 1.35 / 1.15 という同じ強度の配分を別の竜へ替える。以前の表紙の効果を残したり、全記憶取得で人数に倍率を掛けたりしない。表紙を外すとコース本来の来訪者へ戻る。変更は 03 の応援客にのみ作用し、01/02 の購入行動、基礎票、競走結果を変えない。

装いは姿と文章の自己表現。記者服の仕立て直しは独立財布の 45 コインを一度だけ使い、以後の着替えは無料。衣装による売上・配当・着順の補正はない。服はこの試作で所持していた想定と明記し、本編の条件衣装を獲得した扱いや報酬 CG の先出しにしない。

予想に添える根拠は **記憶 1 枚＋理論 1 枚**。異なる寄り道で得た記憶と理論を自由に結べる。どれを付けても勝率・収支・成功判定を強化しない。公開前は、選んだ上位条件、竜の観察、今日のコース、共有する読みを言葉にする。結果後は、人物からの返事が以下のように具体的に変わる。

- 得意と舞台の理論：対象竜の実着順、2 着以内／2 頭とも 3 着以内という自分の主張、覚えていた竜の trait を受けて、届いた読みと限界を振り返る。特性ひとつが着順の原因だとは断定しない。
- 人気と実力の理論：実倍率・購入票・払戻を使い、的中でも元返しの場合と、外れて払戻がない場合を分ける。「人気薄なら勝てる」という教訓にしない。
- 共有する読みの理論：同じ竜へ頼った記事の枚数、そのうち何枚が的中したか、複勝とワイドの着順条件の違いを返す。券の数を独立した根拠の数と誤認させない。

### 既存要素との境界

`js/meals.js` の食事は表示用の食べ歩き・食材当て・隠し味当てコレクションで、本編のコインやレース経済へ干渉しない。既存「究極のだし巻き卵」の隠し味はマヨネーズ。`js/field_lessons.js` は食べ歩き、旅の読み物、研究街、人助け等が暮らしの実地稽古として蓄積する文脈を持つ。`js/data_assets.js` のミズ・アオラとの出会いには、人気で配当が薄くなること、脚質・コース・天気等を読むこと、読んでも必ず当たるわけではないことが既に描かれている。

一方、「聖なるご飯」「伝説アイテム探索」という名前の固有機構は現コードで確認できなかった。星渡りの祭祀布の探索と聖龍祭の食卓は、既存の古布屋・料理・観光フレーバーを足場にした **試作の新しい場面**。ミズの理論は既存の出会いの振り返り、ほかの取材本文は試作で加えた文章として区別する。聖域の奥を暴く画像や新しい実在報酬であるかのような表示はしない。

使用画像は古布屋・商店街・だし巻きの既存画像と、所持想定を明記した衣装立ち絵。`images/cg/*` は使用しない。人物の新しい返事は本試作の結びとして作ったもので、既存本編の台詞を勝手に書き替えない。本編のセーブを読み込まないため、実プレイヤーが本編で何を所有・体験したかは判定しない。

`activeScene` は `{placeId,title,image,body,choices:[{id,label,detail?}]}`、`notice` は `{kind,title,body}`。本文は文字列。`getView(state).journey` に同じ旅 view、`scenario.fanSource` に招いた読者名を返す。記憶の `readerGroup.fans` は `{id,name,interest}` の配列で、選択前に誰を招くのか見せる。

`preview.features[].evidence` は `{memoryId,theoryId,memoryTitle,person,quote,memoryImage,theoryTitle,theorySource,observation,claim,connection,relatedIds}`。着順や実払戻を含めない。

`resolve.chronicle` は `{outfit,cover,entries,closing}`。entries は根拠のある記事だけを含み、evidence に `{slot,predictionId,title,resultLine,reply,review}` を加える。closing / resultLine / reply / review は文字列。reply は人物名 prefix を含まない短い手紙、review は理論と実着順・票の講評。結果 UI は人物の手紙を先に、根拠と数字を必要に応じて読み返せる構成にする。

独立プレイで、最初の布の探索は入口から答えが見え、一度調べるだけで理論を得るため発見が軽いとの指摘を受けた。入口から答えの言葉を外し、発見した三つの痕跡からどこまで言えるかを店主へ返す段階を追加した。また、理論の講評だけでは人物との総決算が弱かったため、表に出す返事を記憶別の短い手紙へ変更。布売りは一緒に裏返した布と次の旅の跡、仕立て屋は選んだ服と次のほつれを直す約束、食堂の人は残してある一切れと席について返す。予想が外れても、出会いそのものは取り消さない。

食卓の理論は味の感想だけから飛躍させず、常連が以前買ったポロ複勝と、旅人のライオウ×ポロのワイドを話題にする会話を加えた。違う券でも同じポロの走りに頼っていたと、自分で聞き比べたことが理論の出典になる。UI では記憶を画像カード、理論をボタンで選び、発行前に生成される主張と結び付けを確認できる。結果には旅写真を並べ、人物の手紙を表に、理論と実着順の講評を折り畳みに置く。

検証は、各寄り道の誤選択・別解・再訪・衣装の二重請求防止・未取得記憶の拒否・画像実在を含む。理論や衣装を変えてもレースと会計は不変、表紙は効果が重ならず解除で元へ戻ることを確認する。さらに全 3 コース×全 3 表紙×全 2,184 紙面を列挙し、競走不変・公開前結果非参照・複数の成立する紙面があることと、ある表紙が他の表紙を全紙面で上回るわけではないことを検証する。

自然な初手にも罠が残る。海風のライオウ複勝・フガク複勝・ライオウ×フガクと、雲上のライオウ複勝・ソウテン複勝・ソウテン×フェニックスは、掲載先を替えることで全的中のまま成功できる。峡谷のライオウ複勝・ヨミ複勝・ライオウ×ヨミは旧予算では 6 通り全て赤字だったが、現在は標準表紙で最善 +1.49 に立て直せる。ただし衣装表紙では同じ 3 枚の最善でも −12.58 となり、別の表紙か予想を考える必要がある。

**利益最大化への偏りは未解決。** 全準備・全表紙で、最大利益だけを狙う紙面は 0〜1 的中であり、成功条件を満たさない。成功紙面に限っても最高利益は全て 2 的中で、全的中の最高利益より高い。標準表紙での全的中最高利益は海風 182.86、峡谷 188.08、雲上 132.86。会計上の利益をそのままミミの評判・最良評価・報酬ランキングにすると、外れる記事を意図的に売る誘因を強める。その用途での本編採用はしない。

難しさも均一ではない。2 枚以上当たった紙面に絞って黒字になる比率は海風 75.8%、峡谷 39.2%、雲上 80.4%。峡谷は予想を読む難しさよりも会計の難しさが強い。全的中赤字を予想ミスと扱わず、最低払戻の補填と届け先の差を結果で示す必要がある。新しい予想のドキドキを長期間支えるには、固定記録の比較だけでは不足する。

採否は **短時間の予想・紙面比較ゲームとして仮組み可、本編の最終ルールの置換は保留**。準備の効用、複数の正しい読み、再編集する理由は検証できたが、長期の面白さや物語全体の難易度を検証したとはしない。本編由来の任意のスカウト部分集合は上記「最小／全記録」の 96 条件とは別であり、同じ成立保証を拡張しない。不足記録を無料の試作用資料で補って比較できる導線を残し、未取材で存在しない手札をプレイヤーの読み違いとして責めない。

## 中盤の判断を終章へ残す「読みの手帖」

第 3〜4 話から新しい予想ミニゲームを重ねるのではなく、**既存の事前判断を、その一戦の実記録として任意に残す**。本編には既に `BET_REASONS` の好み／能力データ／レース展開／うまみを選ぶ操作があり、結果画面は `betStoryOf` / `reasonReplyLine` で選んだ竜と区間の順位を照合している。追加価値は、それまで集計しか残らなかった自分の一戦を、次のレースや終章でも読み返せることに置く。記入ノルマ、新しい報酬、コイン、読者数や能力のボーナスは加えない。

小さい一周は「いつもどおり理由を選んで賭ける→確定した結果から残したい一戦だけ手帖へ→後の同じ竜／地域で前の自分を読む→終章で今回の予想へ結ぶ」。結果を見てから新しい事前理由へ書き換えるものではない。保存する理由は、その出走前に確定した `c.betReasonUsed` だけを使う。保存は 6 件まで、自動で大切な記録を消さず、満杯なら自分で整理する。

### 既存記録から言える範囲

- `kikoCourse` は地域別の出走数・的中数・最後に見た勝者名。過去の具体的なレース、対象竜の着順、区間順位は復元できない。
- `collection[id].records` は観察回数・1 着／3 着内の回数等の集計。いつ、どのコースで走ったかは残らない。
- `KIKO_SERIAL` は第 3 話から行政街、暮らしの発展から温泉・棚田、出走や的中からコース記事へ続く既存の取材路。書き上げの間に一戦を挟む仕組みを持つ。手帖を連載の必須条件や追加の待ち時間にはしない。
- `scoutMemo` は交流でうまくいった接し方の記憶。走力や勝率を示す観測結果へ読み替えない。

したがって、具体的な一戦の保存は今回の機構を使って結果から残した時点で始める。古いセーブの集計から架空の過去レースを補完しない。区間の情報が取れない時は「途中の順位は記録していない」と表示する。

### 引き継ぐのは竜の答えでなく、見る場所

本編中盤の初期 8 頭はルベル、セラム、ポロ等で、終章試作の 8 頭とはほとんど重ならない。手帖を最終 8 頭だけに制限せず、本編の全竜を対象とする。終章で違う竜の記事に添えた場合は、その違いを明記する。

| 当時選んだ理由 | 今回へ持ち込む読み方 |
| --- | --- |
| 好み | 応援する気持ちと、届く着順を分けて見る。 |
| 能力データ | 一つの能力だけでなく、区間でどう走ったかを確かめる。 |
| レース展開 | 序盤・中盤から最後まで、順位の移り変わりを見る。 |
| うまみ | 人気の順位と、実際に届いた着順を分けて見る。 |

例として、本編で「能力データ」を理由に選んだルベルが 3 着で複勝的中だった記録を、今回のフガク複勝へ添えられる。公開前に「別の竜・別のレース」「本編複勝は 3 着以内、今回の記事は 2 着以内」を明示。結果ではルベルの実記録と今回のフガクの実着順を並べる。過去の的中や、選んだ理論が今回の的中を保証する説明はしない。

### 中盤から終盤への実操作確認

第3話の隔離チェックポイントから、通常の投票券で「レース展開」を選び、実際のレース・払戻・精算エンジンを動かした。結果からルベルの一戦を任意で残し、紀行での再読、同じ竜の次の出走表の表示、終章経済画面からの引き継ぎ、フガクの記事への添付、最終比較まで一周を確認。記録追加で元の着順・払戻・財布は変化せず、同じ結果を二重保存せず、試遊中の本編localStorage書き込みもなかった。375pxと1280pxで画像と操作を確認し、console/HTTPエラー0。案内やログイン演出は検証用チェックポイントで抑止し、長い中盤の通しプレイとは区別する。

独立Astraも実レースから生成した引き継ぎURLを使い、ルベルの記録だけをフガク複勝へ添えて全的中・+101.9を実操作した。具体的な元レース・事前理由・結果へ戻れる点は、抽象的な理論だけより明確な改善と評価。一方、経過を比較する目的が長い説明に埋もれるとの指摘を受けた。結果には過去の実順位推移・記録した区間と、今回の公開条件・実着順を短いカードで並べ、詳しい読み直しは閉じた詳細へ移した。過去の的中が今回の成功を証明するとは扱わない。

終章の現試作は固定タイムの短縮再生で、区間順位を保存していない。そのため今回は最終着順までを比較し、欠けた区間は「記録なし」と表示する。架空の追い上げや因果を補って総決算の演出にしない。中盤を本人が長く遊んで選び残した記憶の重み、章3〜4の所要時間と全体テンポ、人間の初見評価は未検証である。

### 手帖の API

共有の `ReadingJournal` が記録を検証し、本編側では実在竜 catalog と確定済みレースに照合して取り出す。終章 engine は本編セーブへアクセスせず、bridge で渡された `state.readingNotes` だけを読む。旧環境で共有 module が未読込なら空配列として扱う。

```js
{
  id: 'race-12', completedRace: 12,
  raceId: 'race_grandclock_1', raceName: '新人競竜杯', region: 'グランドクロック地域',
  reason: 'data', // kan | data | tell | value。出走前に確定した理由
  betType: 'place', hit: true, // 本編の的中条件との矛盾は拒否
  selections: [{ dragonId: 'rubel', name: 'ルベル', rank: 3 }],
  trace: { dragonId: 'rubel', earlyRank: 1, midRank: 2,
    section: '終盤の直線', stat: '速さ', pace: '標準', popularity: 1 }
  // trace は観測できた一頭ぶんだけ。欠損時は null
}
```

`getReadingNotes(state)` は検証済み snapshot に `title, sourceLabel, reasonLabel, observation, reviewText, suggestedTheoryId, image` を加え、最大 6 件を返す。`getView(state).readingNotes` にも同じ配列を返す。能力データ／展開には `terrain`、うまみには `market` を候補として返すが、理論を自動獲得したり、選択を強制したりしない。

`preview/resolve(state, plan, annotations)` の各注釈へ `readingNoteId` を追加。記憶・理論と併用でき、手帖一枚だけでもよい。持ち込まれていない ID は拒否。`evidence.readingNote` は表示用 snapshot と `sameDragon`（過去と今回の対象に共通の竜がいるか）を含む。`connection` は公開情報だけで読み方の転用を説明し、`chronicle.review` は保存された過去の事実と今回の実着順を比較する。手帖を添えても race、会計、成功判定は不変。

これは「昔の自分が実際に選んだ理由」が最後まで残る接続であり、集計から理論を自動採点する機構ではない。本編全体の長期体験が完成したという評価は、実際に中盤から遊び、残した記録を後で読み返すテストを経て判断する。

engine 回帰は全件 PASS。従来の競走不変 105,120 件・隠れ着順非参照 6,579 件を維持し、4 理由×3 コースの手帖あり／なし比較 12 件と、手帖付き preview の隠れ結果非参照 1 件を追加した。ルベルからフガクへの転用、同じ竜の別レースとしての比較、区間記録なしの表示、記憶／理論との併用、存在しない手帖 ID の拒否、取得した表示データから原記録を書き換えられないことも確認した。
